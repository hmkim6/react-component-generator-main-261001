# TDD Rule

> **이 규칙은 Rigid — 상황에 맞게 변형하지 마라.** 단계를 건너뛰거나 순서를 바꾸거나 "이번만" 예외를 두지 않는다.

## 우선순위

- 프로젝트의 `CLAUDE.md` 또는 `AGENTS.md`에 TDD 규칙이 있으면 **그 규칙이 이 파일보다 우선**한다.
- 이 파일은 프로젝트 규칙이 없을 때 적용하는 **기본값(fallback)** 이다.
- 테스트 실행 명령은 프로젝트 문서에 적힌 것을 쓴다 (이 저장소: `bun run test <파일>`).

## 적용 기준

**TDD 필수**

- 비즈니스 로직 (도메인 규칙, 상태 전이, 계산)
- API (라우트 핸들러, 요청 검증, 응답·에러 형식)
- 유틸 함수 (파싱, 변환, 정규화, 재시도/폴백)
- 버그 수정 (**버그를 재현하는 실패 테스트가 먼저**)
- 동작이 있는 커스텀 훅, 폼 검증, 조건부 렌더링 로직

**TDD 불필요**

- 타입 정의, 인터페이스
- 설정 파일 (빌드, 린트, tsconfig, 환경 설정)
- 순수 UI (마크업, 스타일, 레이아웃, 문구 변경)
- SQL (스키마, 마이그레이션, 쿼리 파일)

판단이 애매하면 **필수 쪽으로 분류**한다. 순수 UI 안에 분기·상태 로직이 섞였다면 그 로직은 필수 대상이다.

## RED-GREEN-REFACTOR

### RED

- **하나의 동작 = 하나의 테스트.** 한 테스트에 여러 동작을 묶지 않는다.
- 테스트 이름은 검증할 동작을 문장으로 쓴다.
- **반드시 실행해서 실패를 확인한다.** 실행하지 않은 테스트는 RED가 아니다.
- **실패 이유가 "기능 미구현"이어야 한다.** 문법 오류, import 오류, 오타, 잘못된 셋업으로 실패했다면 RED가 아니다. 테스트를 고쳐 올바른 이유로 실패할 때까지 다시 실행한다.
- 처음부터 통과하는 테스트는 아무것도 검증하지 못한다. 테스트를 의심하고 다시 작성한다.

### GREEN

- 테스트를 통과시키는 **최소한의 코드만** 작성한다.
- **YAGNI:** 아직 테스트가 요구하지 않는 분기, 옵션, 일반화, 예외 처리를 넣지 않는다.
- **신규 테스트와 기존 테스트가 모두 통과**하는지 전체 테스트를 실행해 확인한다.
- 기존 테스트가 깨지면 테스트를 고치지 말고 구현을 고친다. 테스트가 틀렸다고 판단되면 근거를 먼저 밝힌다.

### REFACTOR

- 허용: **중복 제거, 이름 개선, 헬퍼 추출**, 구조 정리.
- 매 변경 후 테스트를 실행해 **green을 유지**한다. 깨지면 즉시 되돌린다.
- **새 동작 추가 금지.** 새 동작이 필요하면 다음 RED에서 시작한다.
- 테스트 코드도 리팩터링 대상이다.

### 반복

- 다음 동작을 하나 골라 **RED로 돌아간다.**
- 요구된 동작이 모두 테스트로 덮일 때까지 사이클을 반복한다.

## 삭제 강제 규칙

- 테스트보다 프로덕션 코드를 먼저 작성했다면 **그 코드를 삭제하고 RED부터 재시작**한다.
- **"참고용"으로 남기는 것도 금지**다. 주석 처리, 다른 파일로 옮기기, 임시 브랜치·스크래치 보관 모두 포함한다.
- 삭제한 코드를 보고 다시 타이핑하지 않는다. 테스트가 이끄는 대로 새로 작성한다.

## 변명 차단표

| 변명 | 반론 |
| --- | --- |
| "너무 단순해서 테스트 불필요" | 단순하면 테스트도 30초면 끝난다. 단순한 코드일수록 경계값·빈 입력에서 깨지고, 아무도 의심하지 않아 오래 숨는다. |
| "나중에 추가하겠다" | 나중은 오지 않는다. 구현 후 작성한 테스트는 구현을 따라 쓰게 되어 통과만 확인할 뿐 설계를 검증하지 못한다. |
| "시간이 없다" | 디버깅과 회귀 수정이 테스트 작성보다 비싸다. 시간이 없을수록 되돌아갈 여유도 없다. |
| "삭제하면 낭비" | 이미 쓴 코드는 매몰비용이다. 검증되지 않은 코드를 남기는 비용이 다시 쓰는 비용보다 크고, 두 번째 작성은 더 빠르다. |
| "프로토타입이다" | 프로토타입은 대부분 그대로 프로덕션이 된다. 정말 버릴 코드라면 이 저장소에 커밋하지 않는다. |
