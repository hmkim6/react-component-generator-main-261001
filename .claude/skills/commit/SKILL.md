# commit: 변경사항 분석 후 컨벤션 커밋

작업 트리의 변경사항을 읽고, 논리적 단위로 나눠 커밋 계획을 세운 뒤, **사용자가 승인한 다음에만** 커밋한다. 사용자가 인자로 범위나 메시지 힌트를 주면 그것을 우선한다.

## 워크플로우

### Step 0: 저장소 확인

- `git rev-parse --is-inside-work-tree`로 git 저장소인지 확인한다. 저장소가 아니면 그렇다고 알리고 `git init` 여부를 묻는다. 묻지 않고 초기화하지 않는다.
- 저장소 루트의 `AGENTS.md`(없으면 `CLAUDE.md`)에 커밋 규칙이 있으면 이 문서보다 그 규칙을 우선한다.
- `git log --oneline -10`으로 기존 커밋 메시지 스타일을 확인하고, 이 문서의 형식과 크게 다르면 기존 스타일을 따를지 사용자에게 알린다.

### Step 1: 변경사항 수집

다음을 모두 확인한다. `git diff`만으로는 새 파일과 스테이징된 변경이 빠진다.

```bash
git status --short          # 수정·추가·삭제·미추적 파일 목록
git diff --staged           # 이미 스테이징된 변경
git diff                    # 스테이징 안 된 변경
```

- 미추적 파일은 내용을 직접 읽어 무엇인지 파악한다.
- 이미 스테이징된 파일이 있으면, 사용자가 그 묶음을 의도한 것일 수 있으므로 계획에서 그 묶음을 먼저 보여주고 유지할지 묻는다.
- 변경사항이 없으면 "커밋할 변경사항이 없습니다"라고 알리고 종료한다.

### Step 2: 커밋에서 뺄 파일 걸러내기

다음은 커밋 계획에 넣지 않고, 발견하면 따로 알린다.

- 비밀값이 든 파일: `.env`, `.env.*`(`.env.example` 제외), `*.pem`, `*.key`, 자격증명 JSON 등. diff 안에 API 키·토큰처럼 보이는 문자열이 있어도 같이 경고한다.
- 생성물·의존성: `node_modules/`, `dist/`, `build/`, `coverage/`, `.DS_Store` 등. `.gitignore`에 빠져 있으면 추가를 제안한다.
- 디버깅용 임시 파일, 스크래치 파일.

lock 파일(`bun.lock`, `package-lock.json` 등)은 `package.json` 변경과 같은 커밋에 넣는다.

### Step 3: 논리적 단위로 분류

변경을 "하나의 이유로 설명되는 묶음"으로 나눈다.

- 하나의 기능 추가와 그 기능의 테스트·스타일은 한 커밋이다.
- 서로 무관한 버그 수정, 리팩터링, 의존성 변경, 설정 변경은 각각 다른 커밋으로 나눈다.
- 한 파일에 서로 다른 목적의 변경이 섞여 있으면 `git add -p`(대화형이라 사용 불가) 대신 해당 파일을 어느 커밋에 넣을지 판단하고, 나누기 어렵다면 그 사실을 계획에 적는다.
- 나눌 이유가 없으면 억지로 쪼개지 않는다. 커밋 1개도 정상이다.
- 커밋 순서는 의존 관계를 따른다. 예: 의존성 추가 → 그것을 쓰는 기능.

### Step 4: 커밋 메시지 작성

형식:

```
<type>: <한국어 요약>

<선택: 본문. 무엇을 왜 바꿨는지 1~3줄>
```

| type | 쓰는 경우 |
| --- | --- |
| `feat` | 사용자가 체감하는 기능 추가·변경 (UI 개편 포함) |
| `fix` | 버그 수정 |
| `refactor` | 동작 변화 없는 코드 구조 개선 |
| `chore` | 의존성, 설정, 빌드, 문서, 스킬 파일 등 그 외 |

요약 작성 규칙:

- 50자 안팎, 마침표 없이, "~추가", "~수정", "~개선"처럼 명사형으로 끝낸다.
- 파일 이름이 아니라 무엇이 바뀌었는지를 쓴다. `App.tsx 수정`이 아니라 `API 키 누락 시 인라인 경고 표시`.
- 본문은 요약만으로 이유가 드러나지 않을 때만 쓴다.
- 환경이 커밋 메시지에 붙일 attribution 줄(예: `Co-Authored-By`)을 지정하면 메시지 끝에 붙인다.

### Step 5: 계획 보여주고 승인받기

커밋 전에 다음 형태로 계획을 보여준다.

```
커밋 계획 (2개)

1. chore: 레트로 테마용 폰트 패키지 추가
   - package.json, bun.lock

2. feat: 플래티넘 데스크톱 스타일로 전체 UI 개편
   - src/App.tsx, src/App.css, src/index.css, src/components/*.tsx

제외: .env (비밀값), dist/ (빌드 산출물)
```

그다음 AskUserQuestion으로 "이대로 커밋 / 메시지 수정 / 분류 변경 / 취소" 중 하나를 고르게 한다. 수정 요청이 오면 계획을 고쳐 다시 보여주고 다시 승인받는다. **승인 없이 커밋하지 않는다.**

### Step 6: 커밋 실행

승인된 계획대로 커밋마다 파일을 명시해서 스테이징하고 커밋한다.

```bash
git add -- <파일들>
git commit -m "$(cat <<'EOF'
<type>: <요약>

<본문>
EOF
)"
```

- `git add -A`나 `git add .`는 쓰지 않는다. 제외한 파일이 섞여 들어간다.
- 계획에 없는 파일이 스테이징돼 있으면 커밋 전에 멈추고 알린다.
- pre-commit 훅이 실패하면 `--no-verify`로 우회하지 않는다. 실패 내용을 보여주고, 고칠지 사용자에게 묻는다.
- `--amend`, `push`, `reset`, 브랜치 변경은 사용자가 명시적으로 요청할 때만 한다.

### Step 7: 결과 보고

`git log --oneline -n <커밋 수>`로 만들어진 커밋을 보여주고, 커밋되지 않고 남은 변경(제외한 파일 포함)이 있으면 함께 알린다.
